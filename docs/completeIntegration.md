# Steps used for creating the Snowflake and S3 integration

Snowflake → AWS S3 Storage Integration Setup, steps to follow 

### **Step 1:** Create the S3 Bucket

- Create an S3 bucket..
- Create the folder/prefix where Snowflake will write files (e.g., test-folder/)..

### **Step 2:** Create an IAM Policy

- Create an IAM Policy granting:

```
s3:PutObject
s3:GetObject
s3:DeleteObject
s3:ListBucket
s3:GetBucketLocation
```

- Restrict the permissions to your bucket/prefix.

### **Step 3:** Create an IAM Role

- Create a new IAM Role..
- Attach the IAM Policy from Step 2..
- Use a temporary trust policy (e.g., your own AWS account root) only so the role can be created..
- Note down the Role ARN..

Example:

```
arn:aws:iam::<AWS_ACCOUNT_ID>:role/snowflake-s3-unload-role
```

### **Step 4:** Create the Snowflake Storage Integration

Run:

```sql
CREATE STORAGE INTEGRATION s3_export_int
TYPE = EXTERNAL_STAGE
STORAGE_PROVIDER = 'S3'
STORAGE_AWS_ROLE_ARN = '<ROLE_ARN>'
ENABLED = TRUE
STORAGE_ALLOWED_LOCATIONS = (
  's3://<bucket>/<prefix>/'
);
```

This tells Snowflake:

"Whenever you need to access S3, use this IAM Role."

### **Step 5:** Retrieve Snowflake's AWS Identity

Run:

```sql
DESC INTEGRATION s3_export_int;
```

Save the following values:

- STORAGE_AWS_IAM_USER_ARN.
- STORAGE_AWS_EXTERNAL_ID.

These are generated by Snowflake.

### **Step 6:** Update the IAM Role Trust Policy

Replace the temporary trust policy with:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "<STORAGE_AWS_IAM_USER_ARN>"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "<STORAGE_AWS_EXTERNAL_ID>"
        }
      }
    }
  ]
}
```

This allows only Snowflake to assume the role.

### **Step 7:** Create the External Stage

```sql
CREATE STAGE my_s3_export_stage
STORAGE_INTEGRATION = s3_export_int
URL = 's3://<bucket>/<prefix>/'
FILE_FORMAT = (TYPE = CSV);
```

### **Step 8:** Test the Integration

```sql
COPY INTO @my_s3_export_stage/test
FROM (
    SELECT CURRENT_TIMESTAMP
)
FILE_FORMAT = (TYPE = CSV)
HEADER = TRUE;
```

### If successful, a CSV file should appear in the specified S3 folder.

# Created an IAM user for JARVIS on AWS to connect to S3 bucket created above ( as now aws account / IAM user was configured )

### Note : using zap-staging - need to replicate in zap-prod

### Steps used :

## 1. Create the policy first (so you can attach it during user creation)

1. In IAM, left sidebar → **Policies** → **Create policy**.
2. Switch to the **JSON** tab and paste this (replace YOUR_BUCKET_NAME with your actual EXPORT_S3_BUCKET value):

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "BucketAccess",
            "Effect": "Allow",
            "Action": [
                "s3:ListBucket"
            ],
            "Resource": "arn:aws:s3:::{{YOUR_BUCKET_NAME}}"
        },
        {
            "Sid": "ObjectAccess",
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:PutObject",
                "s3:DeleteObject"
            ],
            "Resource": "arn:aws:s3:::{{YOUR_BUCKET_NAME}}/*"
        }
    ]
}
```

A couple of notes on this policy:

- Resource ends in /* — this grants access to *objects inside* the bucket, which is what PutObject/GetObject/DeleteObject need. It does **not** grant ListBucket (that needs the bucket ARN itself, without /*) — the code we wrote doesn't list the bucket anywhere, so this is deliberately left out. If you ever need aws s3 ls to work with this same key, you'd add a second statement for s3:ListBucket on arn:aws:s3:::YOUR_BUCKET_NAME (no /*).
- If you want to scope it even tighter to just the exports/-style prefix this module writes under (per the EXPORT_S3_* config and the client_id/year/uuid.csv key pattern), you could restrict Resource further, but since the whole bucket is presumably dedicated to this export feature, bucket-wide object access is reasonable.

3. Click **Next**, give it a name like {{YOUR_BACKEND_POLICY_NAME}}, add a description if you like, and **Create policy**.

## 2. Create the IAM user

1. IAM → **Users** → **Create user**.
2. User name: {{YOUR_BACKEND_USER_NAME}}.
3. **Do not** check "Provide user access to the AWS Management Console" — this user only needs programmatic access, no console login.
4. Click **Next**.
5. On the permissions step, choose **Attach policies directly**, search for {{YOUR_BACKEND_POLICY_NAME}} (the one you just made), check it.
6. **Next** → **Create user**.

## 3. Generate the access key

1. Click into the new {{YOUR_BACKEND_USER_NAME}} user → **Security credentials** tab.
2. **Access keys** section → **Create access key**.
3. Use case: **Application running outside AWS** (or "Third-party service", depending on how AWS phrases it in your console).
4. Copy AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY immediately — the secret won't be shown again.
5. Add both to your .env.
